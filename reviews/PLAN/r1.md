# PLAN.md 独立レビュー r1

- 対象：`PLAN.md`（`CONCEPT.md` を基準に照合）
- 確認日：2026-11-01。環境の確認は読み取り専用のコマンドのみで行った。コンテナ、ネットワークの変更と `claude` セッションの起動はしていない。
- 集計：**blocker 3 / major 25 / minor 12**

## 要約

通過できない主な理由は次の3つである。

1. レビューの独立性とゲートの改ざん防止は、ホスト上で実施する手段がなく、文面上の約束にとどまる。
2. ゲートの論理では、まともな品質の成果物でも通過できない可能性が高い。
3. パイロットで不具合が見つかったときに戻る経路がない。

このほか、言語間の公平性（段階間の記憶、Python ハーネス、打ち切り条件、インフラ再実行）、統計（1課題からの検出力、H2 の課題数、分析単位）、予算にも、実行前に直すべき欠陥がある。

## Blocker

### B-1 レビューの独立性とゲートの保護を、ホストのセッションで強制できない

**該当**：§1「作成側のAIは…判定の変更ができない」、§3.1 の「読めないもの」、§5「P0〜P3 の作成とレビューはホストのログイン認証で行う」

§3.1 の読み取り制限には、実施手段の記述がない。コンテナで隔離されるのは解答者だけである。G0 の試験も「カナリアと外部通信」で、これは解答者の分離を試すものである。作成者とレビュアーの分離を試す項目は「ゲートを迂回できないこと」の一言しかない。

**実測の根拠**
- `claude auth status` は `authMethod: claude.ai`、`projectsDirectory: /home/coxless/.claude/projects`。ログイン認証のホストセッションは、すべて同じ `~/.claude` を共有する。`history.jsonl`、`file-history`、`shell-snapshots` も同じ場所にある。
- `--help` によると、`--bare` は「OAuth and keychain are never read」である。§2.1 に挙げた `--bare` は、ログイン認証で動く P0〜P3 のセッションでは使えない。したがって、自動メモリと CLAUDE.md の読み込みを `--bare` で止める手段は、この期間には使えない。
- レビュアーには §3.3 で検証の実行（テスト、攻撃、再計算）を求めている。つまり Bash を持つ。作成者と同じ UID で動くなら、ファイル権限では何も防げない。

**失敗シナリオ**
1. G3 のレビュアーが Bash で `~/.claude/projects/-home-coxless-development-typed-or-not/*.jsonl` を読む、または自動メモリが自動で読み込まれる。作成者の思考と自己評価がレビュアーに渡る。レビュー記録には残らない。
2. 同じ作業ツリーの `reviews/<gate>/r1.json` を、ラウンド2のレビュアーが読む。§3.2 の5「過去のレビューを見ない」が破られる。
3. 作成者が、同じ UID で `state/phases.json`、`reviews/<gate>/r<N>.json`、`harness/orchestrate.py` を書き換える。判定はスクリプトが JSON から機械的に行うので、書き換えた JSON がそのまま「通過」になる。
4. 通過と判定された時点の成果物と、コミットされた成果物を結びつける仕組みがない（§4「ゲートを通過して初めて…コミット」）。レビュー中や通過後に変更しても検出できない。

**必要な対応**：作成者とレビュアーも役割ごとの使い捨てコンテナで動かし、成果物はハッシュを固定した読み取り専用のコピーで渡す。`state/`、`reviews/`、`harness/orchestrate.py` はセッションから書けない場所に置く。判定には成果物のハッシュを記録し、コミット時に照合する。ログイン認証をコンテナに入れられない制約（§5）と衝突するため、P0〜P3 の認証方式から決め直す必要がある。これらを G0 の試験項目にする。

### B-2 ゲートの論理が収束せず、計画全体が完了できない可能性が高い

**該当**：§3.2 の3〜6、§3.3、§4、§6

次の4点が重なる。

1. **棄却した指摘が復活する**：§3.2 の5では、新しいレビュアーは過去のレビューを見ない。裁定者が棄却した指摘も知らないので、同じ指摘を再び `major` として出す。§3.2 の3の判定は JSON の機械的な判定なので、不合格になる。棄却済みの指摘の照合（同一性の判定）は定義されていない。
2. **判定の時点が矛盾する**：§3.2 の3は「`blocker` と `major` が0件のときだけ通過」とし、§3.2 の4は「棄却を認めた指摘だけを閉じる」とする。全指摘が棄却された場合に通過なのか、次のラウンドが必須なのかが読み取れない。後者なら、3ラウンド目で全棄却でも停止する。また、3ラウンド目の指摘を修正した結果を確認する機会がない。
3. **ゼロ件の基準と毎回の白紙レビュー**：毎回新しいレビュアーが欠陥を探すよう指示されるので、指摘の集合は毎回変わる。修正で新しい欠陥が入る可能性もある。上限は3回である。2名のゲートで判定をどう合わせるかも定義がない。
4. **ゲートの直列**：G0〜G10 の11個すべての通過が必要である。

**反証可能な見積もり**：1ラウンドの通過確率を q とすると、1ゲートの通過確率は 1-(1-q)^3、全11ゲートでその11乗となる。q=0.5 で 23%、q=0.3 で 1%である（棄却の復活を考慮しない甘い値）。参考として、本計画の1回目のレビューでも、本書のとおり多数の `major` が出ている。

**必要な対応**：棄却済みの指摘の台帳を機械的に照合する（レビュアーには見せず、判定時に突き合わせる）。ゲート通過の式を一意に定義する。上限を増やすか、前ラウンドからの差分だけに新規の `major` を認める確認ラウンドを設ける。導入前に、G0 の実データで収束するかを試す。

### B-3 後戻りの経路がなく、実行フェーズのゲートでは「修正」が定義されていない

**該当**：§3.2 の4・6、§4 の P5/P8/G5/G8、§6、`CONCEPT.md` §9「ハーネスの不具合…の漏れを確認」「課題の難易度を調整」

パイロットの目的は、ハーネスの不具合と分離の漏れ、難易度の問題を見つけることである（CONCEPT §9）。ところが §4 は前進のみで、確定済みの P2〜P4 の成果物を、後のフェーズで変更して再度ゲートを通す手続きがない。

**失敗シナリオ**
1. P5 でテストランナーの不具合が見つかり、20試行が無効になる。P5 の作成者に P4 の成果物を変える権限はなく、変えてよいなら G4 の通過が無効になるが、その扱いの定義もない。結局、3ラウンドで停止するか、未レビューの修正で進むかのどちらかになる。
2. パイロットで v1 の合格率が全条件で 100%（天井効果）、または 0% になる。難易度を調整する工程が P6 にもない（「試行回数、課題数、解析計画」のみ）。天井のまま本実験に進むと、H1 は無意味に「同等」となる。
3. G8 のレビュアーが `major` を出したとき、作成者は何を「修正」するのか。試行の再実行は §6「モデルの出力が原因の失敗は再実行しない」と衝突し、解析の変更は事前登録の逸脱になる。実行後に結果を見て修正できるなら、それ自体が研究者の自由度である。G5・G8・G9 の修正の範囲が定義されていない。

**必要な対応**：フェーズの巻き戻し（影響するゲートの再通過と、影響する試行の全条件での破棄）を定義する。パイロットの難易度基準と調整手順を P6 の前に置く。G5/G8/G9 では修正を禁止し、記録と停止のどちらかに限定するなど、許される動作を列挙する。

## Major

### 独立レビューの実効性

**M-1 P0 の信頼の起点が自己参照である（§1、§3.2 の1、§4 の P0）**
`orchestrate.py` と `reviews/prompts/` は P0 の成果物である。一方、§3.2 の1によれば G0 のレビュアーは `orchestrate.py` が固定のプロンプトで起動する。検証される側の物が検証者を起動し、検証者への指示も決める。「常に通過する」「レビュアーの権限を絞る」プロンプトでも、それを起動する側は同じ作成者である。P0 の作成者を誰が起動するかも書かれていない。G0 は全ゲートの土台なのに、§3.3 の「2名・別モデル」の対象外である。
対応：P0 のゲートは、P0 の成果物に依存しない手順（計画に固定した起動コマンドとプロンプト）で実行する。G0 も2名にする。

**M-2 空洞のレビューでも機械的に通過する（§3.2 の3）**
通過の条件は「`major` 以上が0件」と「検証項目の一覧がある」ことである。一覧の真偽は確認されない。レビュアーが何も実行せずに項目を列挙し、全部 `minor` に評価すれば通過する。レビュアーの検出力を測る仕組みがない。また、作成者は成果物の中（`REVIEW.md`、コメント、コミットメッセージ）に自己評価や「問題なし」の説明を書ける。§3.1 が禁じる要約や自己評価は、この経路で渡る。
反証可能な試験：既知の欠陥を埋め込んだ成果物を各ゲートのプロンプトに通し、検出率を測る工程は計画にない。
対応：G0 で欠陥注入によるレビュアーの校正を行う。実行した検証はコマンドログと照合する。

**M-3 裁定者が事実上、レビューを無効にできる（§3.1、§3.2 の4）**
裁定者は同じモデルの1名で、作成者の棄却理由を読む（作成者の文章が直接届く）。棄却の件数や `blocker` の棄却に制限はなく、裁定の結果を確認するレビューもない。作成者がすべての指摘に説得的な理由を付ければ、人間が見るのは P10 まで先になる。§1 の「検討結果は必ず独立レビュー」の例外になっている。
対応：`blocker` の棄却は2名の一致を要する、裁定者は別モデルにする、棄却率が一定を超えたら停止する、など。

**M-4 要件の基準そのものを作成者が書き換えられる（§2.2、§4 の P1、§3.1）**
P1 の作成者が `CONCEPT.md` を修正し、G1 のレビュアーは更新後の `CONCEPT.md` と照合する。「過去を見ない」ので、元の版との差分も見ない。たとえば作成者が 5.1 の監査の条項を弱めても、基準ごと変わるので検出できない。§4.1 の解決で `PLAN.md` が変わる場合の扱いもない。
対応：開始時の `CONCEPT.md` と `PLAN.md` のハッシュを固定し、G1 に原本と差分を渡す。要件の弱化を観点に明記する。

**M-5 固定プロンプトが、まだ存在しない成果物を前提にする（§3.2 の1、§4）**
全ゲートのプロンプトは P0 で固定し「以後は変更しない」。一方、P1 で指標、回帰の定義、`make check` の中身、比較の家族が変わり、P4 で打ち切りの基準が決まる。G3〜G9 のプロンプトはこれらを具体的に検証できない（または P1 の結論と矛盾する観点を持ち続ける）。変更すると例外になり、変更しないと検証が抽象的になる。
対応：P1 の通過時点で、後段のゲートのプロンプトを一度だけ更新し、独立レビューを通して固定する。

**M-6 ホストのセッションの権限が、計画の禁止事項を実施していない（§1、§2.1、§4 の P0）**
`-p` のセッションは承認を人に求められないので、権限モードを決める必要があるが、計画は解答者のものしか書いていない（§5）。実測では利用者は `lxd` グループに属し（root 相当）、同じ LXD 上で利用者の `dev-*`、`gpu-*` のコンテナが実行中である。また、このセッションには claude.ai の Gmail と Drive のコネクタが見えている。
失敗シナリオ：§3.3 の「分離の攻撃」を実行するレビュアーや、エラーを直そうとする作成者が、他のコンテナやネットワークを変更する、外部にデータを送る、`git push` や Drive 共有で公開する。「公開は人間の承認後」「`workshop` に触れない」は、どちらも指示だけで、強制されていない。
対応：P0 の後の全セッションは `ton-` のコンテナ内で実行し、`lxd` のソケットと claude.ai のコネクタ（`--strict-mcp-config` など）を与えない。

### 自律実行の停止と不正な結果

**M-7 APIキーがなく、自律実行は現時点で確実に P4 で止まる（§1、§5）**
実測：`~/.config/typed-or-not/` は存在せず、`ANTHROPIC_API_KEY` は未設定、契約は Pro である。キーは人間にしか用意できず（Console の組織、入金、ワークスペース、上限）、§5 は P3 まで進めて止まると定める。これは、「人間の関与は最後の1回だけ」（§1）の例外である。§5 に再開の手順はなく、§6 の停止条件にも入っていない。「`FINAL_REVIEW.md` を書いて終了」するのかも不明である。また、3,300 USD の支出が可能かは確認していない（API 組織の利用ティアの月間上限やレート制限は、未確認の前提である。同時4試行で 429 が続けば §6 の 10% に達する）。
対応：開始の前提条件として、P0 の前に人間が1回だけ用意し、残高とレート制限を P0 で検証する。

**M-8 P0 でのフラグ検証が、§5 の認証の制約と矛盾する（§2.1「P0 で動作を検証する」、§5「P4 のスモークテストから必要」）**
`--bare` は APIキーが必須（実測）である。§2.1 が「API利用時のみ」とする `--max-budget-usd` も同様である。コンテナ内の CLI の動作（プロキシ経由の許可先の過不足、自動更新の無効化、`stream-json` によるターン計数、権限のスキップが実行ユーザーで動くか）も、キーなしでは確かめられない。ログイン認証はコンテナに入れない。結局、P0 の検証は実施できず、G0 を通過したあとの P4 で初めて判明する。B-3 のとおり、そこから P0 に戻る経路はない。
対応：P0 にキーを前提として、少額の実走で確認する。

**M-9 停止時の報告がレビューを通らず、P10 との依存も矛盾する（§3.2 の6、§4 の P10、§5、§6）**
§3.2 の6は「依存するフェーズを停止し、未解決の指摘を P10 の報告に載せる」とするが、P10 は全フェーズに依存するので P10 も止まる。§6 は「後続を実行せず `FINAL_REVIEW.md` に書いて終了」とする。そうすると、`FINAL_REVIEW.md` は G10 を通らない。§1 の「例外はない」に反し、最も重要な人間向け資料が未レビューになる。G10 自体が3回で通らない場合の報告経路もない。また、予算の上限で停止すると報告の費用も残らない（§5 の 3,000 USD は P10 までの合計で、予備枠がない）。
対応：停止時の報告を独立した経路とし、固定のレビューと費用の予備枠を持たせる。未レビューなら未レビューと明記する。

**M-10 ハングとクラッシュから復旧する手順がない（§2.2、§5、§6、CONCEPT §5）**
- ターン計数は `stream-json` の流れに依存するが、出力が止まるとターンは増えず、上限に達しない。CONCEPT §5 は実時間の制限を避けるとしており、計画に監視のタイムアウトがない。プロキシの停止や API の応答なしで、`orchestrate.py` は無期限に待つ。
- Pro の制限への対処は「解除まで待つ」だけで、検出の方法と中断したセッションの扱いがない。`--resume` なら文脈が残り、新規なら途中の作業が残るので、レビュアーの場合は独立性にも関わる。
- レビュアーの異常（JSON 不正、途中終了、拒否）が1ラウンドに数えられるかが未定義で、インフラの障害で3ラウンドを消費し得る。
- 本実験は数百時間になる可能性があるが、再起動やクラッシュの後の冪等な再開と、孤立コンテナの掃除が定義されていない。

### 言語間の公平性と分離

**M-11 同じ試行の段階間で記憶が共有される（§3.1「試行ごとの新規コンテナ」、CONCEPT §5「コードだけが記憶」、§5.1「`HOME`…を試行ごとに」）**
CONCEPT と計画は、コンテナと `HOME` の単位を**試行**としているが、段階は同じ試行の中にある。v1 のセッションの `~/.claude/projects/...` の履歴と自動メモリ、`/tmp`、シェルの履歴が v2 のセッションに残る。`--bare` や `--no-session-persistence` の指定も定められていない。これは H2 の前提（「コードだけが記憶」）を壊し、計測の対象を変える。さらに、リポジトリに残るメモ（`CLAUDE.md`、`NOTES.md`）や `.git` の履歴を引き継ぐかも未定で、作りやすさに言語差があれば交絡になる。
対応：段階ごとにコンテナを作り直し、ソースのツリーだけを定められた規則で引き継ぐ。G0 に、段階間のカナリアを加える。

**M-12 参照実装と既存コード課題が、言語間の分離に反する可能性がある（§4 の P3、§2.2、§5.1）**
P3 の「さらに別セッションが4言語の参照実装を」は、1セッションで4言語を書くとも読める。そうすると、テストの妥当性の基準である参照実装が、1言語の設計を訳したものになり、要件と CONCEPT §5.1「1つのセッションから複数の言語を実装しない」に反する。
もっと深刻なのは、6.1 の5（2,000〜5,000行、「各言語で同じ設計に揃えて」）である。分離して書けば設計が揃わず、揃えるには別言語のコードを渡す必要がある。解答者が読むコードに翻訳元の言語の癖が残ると、その言語が有利になる。§2.2 は著者を AI に替えただけで、この矛盾に触れていない。P7 の「作り方は P3 と同じ」にも、既存コード課題の作り方は含まれない。
対応：言語ごとに別セッションとする。既存コード課題の手順を明示するか（言語中立な設計書から各言語で独立に生成し、構造の同等性を計測する）、課題から外して逸脱として記録する。

**M-13 Python のハーネスがコンテナに入ると、`py` だけ有利になり、言語の情報も漏れる（§3.1、§4 の P2、CONCEPT §4、§5.1）**
CONCEPT §4 は共通ハーネスを Python とし、§4 の P2 は `make test` を全条件で動かすと定める。公開テストを実行するには、Python の処理系とハーネスのコードが全コンテナに必要になる（CONCEPT §5.1 のマウントの一覧には入っていない）。すると次の問題が起こる。
- `py` の解答者だけが、テスト基盤を自分の言語で読め、再利用もできる。
- `js`、`rust` の解答者は別の言語の存在を知り、Python で補助スクリプトを書ける。`rust` の中に Python を使う抜け道も生まれる。
- 逆にハーネスをコンテナ外に置くなら、公開テストの実行方法を再設計する必要がある。CONCEPT §6.3「エージェントが読める・実行できる」との兼ね合いが未解決である。
- Node の扱い：CLI がネイティブ版か npm 版かで、`py`・`rust` のコンテナにも Node が入るかが変わる。
対応：公開テストはデータ（入出力の JSON Lines）とし、ランナーは言語に依存しない静的バイナリにする。G2 で各イメージのコマンドの差分を確認する。

**M-14 実験条件の遵守と同一プロンプトの要件が衝突する（CONCEPT §3、§5、§5.1、§4.1）**
`py` の「型ヒントなし」と `js` の「JSDoc 禁止」は、解答者に伝えない限り守られない（モデルの既定は Python で型ヒントを付けることが多い）。伝えれば「言語名・コマンドだけを差し替える」に反し、条件ごとに異なる指示となって、比較を示唆しうる。計画の §4.1 に論点がなく、違反の検出と、違反した試行の扱いもない（分析から除くと選択バイアス、含めると処置が混ざる）。同様に `ts` の `any` 禁止は ESLint の実行が前提で、最終成果物に `any` が残った場合の定義がない。「型検査を実行したか」も計測しないと、H2 の機構を解釈できない。
対応：§4.1 に追加し、最終コードに静的検査をかけて処置の遵守率を主要な報告項目にする。扱いは事前登録する。

**M-15 費用の上限が、差のある打ち切りを生む（§2.2、§5「費用上限は全条件で同じ値」、CONCEPT §5）**
CONCEPT §5 が実時間でなくターンで制限するのは、Rust を不利にしないためである。しかし、計画は同じドル上限を加える。出力やコンパイルエラーでトークン量が言語により異なるので、同額の上限は同じ機会を意味しない。ターン上限と費用上限のどちらが先に発動するかが条件で変わり、Rust や TS で費用の打ち切りが多ければ、合格率の差は上限の効果になる。トークン量（H3）にも、条件で異なる打ち切りが入り、Mann-Whitney の結果は歪む。また、段階の途中で強制停止すると壊れたコードが次へ引き継がれ（§4.1 の3）、差が累積する。§4.1 の6は未完了の扱いだけで、この点を解決しない。
対応：費用上限は暴走防止として十分に高くし、発動率を条件別に報告する。一定を超えたらゲートで不合格とする。H3 は打ち切りを考慮して分析する。

**M-16 インフラ失敗の再実行が、条件で異なる選択バイアスを生む（§6、§2.1）**
- 10% は全体の率なので、`rust` だけ 30% 失敗しても全体では 7.5% で止まらない。
- メモリ制限での OOM kill（Rust のビルド）、ツールの実行時間切れは、インフラかモデル起因かが曖昧である。再実行できる失敗をモデル起因の失敗と分ける線が、条件で異なって働けば、難しい試行だけが引き直しになる。
- 段階 v3 で失敗した場合に、段階だけやり直すのか試行全部かの定義がない。再実行によりブロックの釣り合いも崩れる（§2.2）。
- 基準は P4 で固定となっているが、この点は G4 の観点に含まれていない。
対応：条件別の上限を設け、OOM の扱いと再実行の単位を事前に固定する。再実行の割合を条件別に検定なしで報告し、感度分析（再実行前の結果を失敗と見なす）を事前登録する。

**M-17 分離の監査が誤検出で実験全体を止める（§6「違反が試行の5%超」、CONCEPT §5.1「他の言語の実装への言及」）**
機械的な言及の検査では、`ts` の解答者は当然 JavaScript と Node に触れ、M-13 の構成なら全条件で Python が現れる。`rust` の解答者が「Python と違って」と述べるのも、分離の違反ではない。文字列の照合で判定すると、5% は簡単に超えて §6 で停止する。条件を緩めれば、本当の漏洩を見逃す。パイロットは40試行なので、5% は2試行である。計画に、違反の操作的な定義と誤検出率の確認がない（G4 は「意図的な違反の検出」だけで、偽陽性を試さない）。
対応：G4 に偽陽性の試験を加える。通信とパスの違反（客観）と言及（要確認）を分け、停止の基準は前者に限る。

**M-18 課題の作成者が仮説とパイロットの結果を知っており、課題が事前登録の後に作られる（§3.1、§4 の P6/P7、CONCEPT §6.2）**
- §3.1 では作成者は「前フェーズの成果物」を読める。P7 の前フェーズは P6 で、`PREREGISTRATION.md` にはパイロットの結果が載る。§3.1 の制限（解答側の成果物）は要約に及ばない。P7 の課題作者は、どの条件が有利だったかを知ったうえで課題を作れる。
- CONCEPT §6.2 の表には「型が効きそうな点」があり、仮説を知る作者が型に有利な仕様変更を作りやすい。G3/G7 の観点は「言語中立」だけで、仮説に有利かは問わない。解答者のプロンプトは守られていても、バイアスは課題から入る。
- P6 で解析計画を確定した後に P7 で新しい課題を作るので、確定の時点では課題が存在せず、パイロットも通らない。G7 が通らなければ、事前登録の後に課題数が変わる。
対応：P7 を P6 の前に置くか、P7 の作成者に仮説とパイロットの結果を読ませない（ファイルの範囲を明示する）。各新規課題を少数の試行で確認し、難易度の基準を満たすものだけ使う規則を事前登録する。

### 統計

**M-19 1課題のパイロットからは、課題数の検出力分析ができない（§4 の P6 と §4.1 の5の矛盾）**
§4.1 の5は「1課題では課題のランダム効果を推定できない」と認める。一方で P6 は「パイロットから分散を推定して…試行回数、課題数…を確定」とする。主分析の検出力を決めるのは課題間の分散（と条件×課題の交互作用）で、これは推定できない。結局、仮定した値に依存するのに、計画には感度分析の要求がない。

**M-20 H2 を検定できる課題数が保証されていない（§4 の P7、CONCEPT §2、§6.1）**
H2 は段階的な仕様変更で定義される。ただし、§6.1 の5種類のうち段階型は `ledger` のみが例に挙げられ、「4〜6課題」の内訳の規定がない。段階型が `ledger` だけなら、主要な仮説の H2 は1課題で判定され、課題を一般化できず、`ledger` の性質と区別できない。
対応：段階型の課題の最小数を P1 で定める（予算にも直結する。M-24）。

**M-21 分析単位と統計モデルが、データの構造に合わない（CONCEPT §7.2、§4.1）**
§4.1 は次の点を論点にしていない。
- 同じ試行内で段階（v1〜v4）とテストは独立ではない。Fisher の検定をテストケース単位で行うと、擬似反復で有意差が過大になる。試行単位なら「合格」の二値の定義が必要である（全部合格か、割合か）。CONCEPT の「合格率」は両方の意味に読める。
- CONCEPT のモデルは課題のランダム切片のみである。CONCEPT §10 が述べるとおり、難しさは課題と言語の組み合わせで変わるので、条件×課題のランダム傾きがないと、固定効果の検定は反保守的になる。一方、4〜6課題で傾きの推定は不安定である。
- 回帰件数はカウントで、段階ごとに母数が変わる。§4.1 の3も解釈だけを問い、モデルを問わない。
G1 と G6 の観点（「分岐の余地がない」）は、分岐が一つでも、誤った分析を止めない。観点に「分析単位」を明記すべきである。

**M-22 検出できない規模で実験を進めても G6 を通過する（§5、§4 の G6、§4.1 の2）**
§5 は「上限を超える場合は試行回数を減らし、検出できる効果量を明記する」とし、G6 も明記のみを要求する。意味のある最小効果を下回れない場合に中止する基準がない。
試算：v1 の二値合格、真の合格率 80%、同等の幅 ±10 ポイント、片側 5%、検出力 80% の TOST は、1群あたり約 274 試行（2(1.645+1.282)²×0.16/0.01）を要する。5課題に分けても、課題×条件あたり約55回で、CONCEPT の「10回、可能なら20〜30回」を超える。割合を連続値として扱う（SD 0.15）なら約 39 であり、指標の定義次第で桁が変わる。H1 が「同等」と結論できないまま 3,000 USD を費やす結果が十分あり得る。
対応：最小の関心効果（SESOI）を P1 で定める。下回るなら P6 の時点で確認的な主張をあきらめ、記述的な研究に切り替えるか停止する規則を置く。

### 予算と資源

**M-23 パイロットの予算に余裕がなく、超過すると実験全体が止まる（§5、§6）**
300 USD ÷ 160 セッション = **1 セッション 1.875 USD**（P4 のスモークテスト、P4〜P6 の作成とレビュー、2名の G6 を差し引く前）。計画は実績のない見積もりと認めているが、次が欠けている。
- モデルが決まっていない（§2 にも §5 にも記載なし）。Opus 級か Sonnet 級かで単価が数倍変わり、上限の意味が変わる。
- 減らす手順は本実験に対してのみである。パイロットで単価が2倍なら、§6 で停止し、それ以降は何も行われない。
- P4〜P6 のレビューの費用がどちらの枠か、APIキーかログインか（§5 は P0〜P3 までしか書いていない）が不明である。
- 1セッションの上限を P4 で、スモークテスト（各条件1回）だけから決める。n=4 では決められない。
対応：モデルを確定する。P4 で段階的に費用を実測し、パイロットの縮小や予算の再設定を事前に定める。ただし人間の増額を要する場合は開始時に上限の幅を得ておく。

**M-24 本実験の予算は、CONCEPT の設計を賄えない可能性がある（§5、CONCEPT §7.2、§6.1）**
3,000 USD から P7〜P10 の費用を除く前でも、5課題 × 4条件 × 20回 × 4段階 = 1,600 セッションで **1.875 USD/回**、6課題 × 30回では 2,880 セッションで **1.04 USD/回** である。P7 には 3〜5 課題の仕様とテスト、各4言語の参照実装、最大3ラウンドのレビューが含まれる。2,000〜5,000 行の既存コード課題は、読み込みだけで1回あたりの費用がかなり大きくなり、4言語分の生成費もかかる。CONCEPT §5.1 の「修正が必要なら全条件をやり直す」の費用は考慮されていない。P6 での「再計算」は回数だけを減らす前提で、課題数や段階の削減の優先順位がない。

**M-25 同時実行の上限が、実際の空きメモリを超える（§2.1）**
実測の `free -g`：総量 15GB、使用 8GB、available 6GB、スワップ使用 1GB。`workshop.coxless` プロジェクトで `dev-*` と `gpu-*` が実行中で、`next-server` だけで RSS が 3.6GB ある。4試行 × 2GiB = 8GiB は available を超える。さらに本体の処理とプロキシも必要である。これらは計画の外の負荷で、時間で変動する。結果は、ビルドやテストの遅延とホストの OOM である。Rust のビルドで偏って起き、実時間の指標（CONCEPT §7.1）と M-16 の失敗率を、条件と交絡させる。他の用途にも害が及ぶ。
対応：同時実行は available を試行の前に確認して動的に決める、または2試行に減らす。実時間は副次指標としても注意書きを付ける。

## Minor

- **m-1 ストレージプールの記載がない（§4 の P0、§2.1）**：実測で、唯一のプールは `workshop`（14.8/28.6GiB 使用）で、`default` プロフィールの `devices` は空である。P0 の範囲は「プロフィールとネットワーク」で、「`workshop` に触れない」と矛盾しないためには `ton-` のプールが必要である。書かれていないと、作成者が既存のプールを使うおそれがある。LXD プロジェクトの分離も同様である。
- **m-2 条件名の伏せ方は容易に破れる（§3.3、§4 の G9）**：ログと成果物の `cargo`、`tsc`、拡張子で A〜D は特定できる。B-1 により、同じファイルシステムなら対応表も読める。数値のみに正規化した表だけを渡すなどの定義が必要である。
- **m-3 同時実行のコンテナ間の通信と許可先の範囲（§4 の P0、G0）**：同じブリッジのコンテナ同士の通信を遮断する試験が G0 の「外部通信」に明示されていない。また、許可先の API は `/v1/files` なども含むので、コンテナ内のキーで試行をまたぐ保存が理論上できる。
- **m-4 APIキーの扱い（§5）**：§5 は解答者がキーを読めることを支出上限で許容する。解答者が直接 API を呼ぶと、ターンとトークンの計測から漏れる。プロキシでキーを付与すれば、コンテナにキーを置かなくて済む可能性があり、P0 で確認すべきである。
- **m-5 コンテナ名による情報漏れ（§4 の P0、CONCEPT §5.1）**：LXD のホスト名の既定はコンテナ名である。`ton-rust-012` のような名前は `hostname` で読める。作業ディレクトリのパスも CLI のシステムプロンプトに入る。名前は無意味な乱数にする。
- **m-6 モデルの切り替わりの防止（§6）**：`--fallback-model` があるが、禁止が明記されていない（過負荷時の切り替えは検出できても、そこで §6 の全停止になる）。`--effort` も統制変数として固定すべきである。エイリアスでなく完全なモデル ID を固定する、とも明記されていない。
- **m-7 担当フェーズのない成果物（CONCEPT §5、§8）**：`prompts/template.md` と `README.md` はどのフェーズにもなく、前者はどのゲートの対象でもない。前者は処置の核心である。
- **m-8 分析環境（§4 の P4/P9）**：実測で、ホストに `pip`、`ensurepip`、`statsmodels`、`R`、`make` がなく `sudo` も使えない。混合効果ロジスティック回帰の実行環境が `containers/` のロック対象に入っていない。分析コンテナを明記すべきである。
- **m-9 §8 に手順がない（§8、§3.2）**：本計画のレビューには、固定プロンプト、ラウンドの上限、通過後の修正の扱いがない。レビューの指示は計画の作成側が書いて渡している（§3.2 の1の「固定のプロンプトのみ」の例外）。修正後の再レビューの扱いも定めるべきである。
- **m-10 事前登録の改ざん耐性（§1、§4 の P6）**：公開が P10 の後なので、ローカルのタグと SHA-256 は外部の読者にとって時刻の証拠にならない。作成者は同じ UID で履歴を書き換えられる。実験結果を含まないハッシュだけの外部タイムスタンプなら、§1 の公開の制限にも反しない。ただし計画に認める規定が必要である。
- **m-11 §2.1 の記述の不正確さと未決の項目**：`--help` の `--max-budget-usd` の記述は「only works with --print」で、「API利用時のみ」は明記されていない（§2.1 は推測である）。CONCEPT §7.2 の「可能ならモデルを2種類以上」は、採否が計画のどこにも書かれていない。
- **m-12 H2 と比較の家族の不整合、minor の扱い（CONCEPT §2、§3、§4.1 の7、§3.2）**：H2 は TS・Rust を型ありとするが、CONCEPT §3 は `py`、`rust` を参考とする。§4.1 の7で「主要な検定は `js` 対 `ts`」と定めると、H2 の検定対象が変わるので、変更の記録が必要である。また、`minor` の指摘がどう記録され処理されるかの規定がなく、§7 の報告にも含まれない。

## 確認して問題がなかった点

**環境の主張（実測で一致）**
- Docker・Podman なし。`sudo` はパスワードが必要（`sudo -n` で確認）。
- LXD 6.9（クライアントとサーバー）、`lxd` グループに所属し `sudo` なしで利用可能。`workshop` プールと `workshopbr0` は他の用途で使用中（プールの使用数 38、ブリッジの使用数 9）。
- 16コア、メモリ 15GB（使用 8GB）、ディスク空き 288GB。Node、Rust はホストになし。Git 2.53、作業ディレクトリは未初期化。
- Claude Code 2.1.316、Pro のログイン認証、`ANTHROPIC_API_KEY` 未設定。
- `--max-budget-usd`、`--no-session-persistence`、`--bare`、`--tools`、`--setting-sources`、`--output-format` は `--help` に記載があり、`--max-turns` は記載なし。
- LXD のファイアウォールドライバは nftables で、ネットワーク ACL の機能がある。`images.lxd.canonical.com` と `api.anthropic.com` に到達できる。Docker から LXD への置き換えは実現可能である（ただしプールは m-1）。

**設計上、妥当と判断した点**
- `--dangerously-skip-permissions` の解答者に利用者本人のログイン認証を渡さない判断（§5）。
- 実行順のランダム化とブロック化（§2.2）。時間帯による交絡への対策として適切である。
- ターン上限をハーネスで実施する方針（§2.2）。ただし M-10 と M-15 の補足が必要である。
- 指摘を弱めず、未通過のまま進まないという停止の方針（§3.2 の6）。方向は正しいが、B-2 のとおり収束の条件が欠けている。
- §4.1 の7論点の認識（v4 の名前変更、H1 の TOST、失敗の持ち越し、`make check` の非対称、パイロットの限界）は、どれも実際の問題を指している。
- パイロットのデータを本実験の検定に使わないこと（§4 の P6）と、探索的な分析を分けること（§4 の P9）。
- 第7章の報告の項目（棄却された指摘の全文を含む）と、公開を人間の承認後にする方針。ただし実施の強制は M-6 である。
- CONCEPT §0 の作業順と計画のフェーズの順は、P0 の追加を除いて整合する。CONCEPT §5.1 の分離の項目は、ほぼ §3.1 の参照で引き継がれている（段階の単位を除く。M-11）。
