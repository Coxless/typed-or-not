### 2回ルールの抜け道

**N-4 再レビューなしの修正がハッシュの照合と矛盾し、修正範囲に制限がない（3.1、3.2 の5と6、3.5）**
3.1：「判定には成果物全体の SHA-256 を記録し、コミットの直前に照合する。不一致なら通過を取り消す」。3.2：2回目で通過と判定した後に、作成者が1回修正する。

- 書かれたとおりなら、2回目で `major` が1件でもあれば、修正でハッシュが変わり通過が取り消される。その後の手順はない。
- 修正の後にハッシュを取り直せば通過するが、その場合はレビューされていない内容にハッシュが結びつき、r1 の B-1 シナリオ4が修正の分だけ復活する。

後者でも修正の範囲は制限されない。たとえば G8 の2回目で `minor` を直すセッションが、`PREREGISTRATION.md` の解析の分岐を変えても、どのゲートも検出しない（G9 は「登録との一致」しか見ない）。この修正は「作成者が1回だけ」であり、差分が指摘に対応するかの検査もない。最終報告には載るが、人間が見るのは費用を使い切った後である。

対応：レビュー時のハッシュと修正後のハッシュの両方を記録する。修正は指摘が挙げたファイルと行に機械的に制限する。G3、G7、G8 と分離に関わる成果物では、修正の差分が分析やテストの判定に影響するなら `critical` の確認に回す規則を置く。

**N-5 重大度の判定を誰も検査せず、空の2回目も通る（3.2 の4と5、3.3。M-2 の `not_fixed`）**
通過を止めるのは `critical` だけである。一方、

- 3.3 の校正の基準は「`major` 以上として検出した率」である。実験結果を無効にする欠陥を `major` と評価するレビュアーは校正に合格し、そのゲートは2回目で通過する。その欠陥は1回の未レビューの修正で閉じられる。**校正は、ゲートを実際に止める判定を測っていない。**
- 重大度を確かめる手段がない。作成者は重大度に異議を出せるが（棄却の申請）、裁定者やレビュアーが過小な評価を引き上げる経路がない。
- 3.3 は「全体レビューでは検証項目が空なら無効」とする。2回目は全体の `critical` を判定するが、`critical: 0` で検証項目が空でも無効にならない。さらに照合はツール呼び出しの存在だけを確認するので、無関係な `true` の実行でも結びつけられる。

対応：校正に「`critical` 級の欠陥を `critical` として検出した率」を別に設ける。2回目にも、全体を確認した検証項目を必須にする。`major` のうち「実験結果の無効化につながり得る」ものを1名の別レビュアーが再評価する手順を、回数に数えずに加える。

**N-6 校正の順序が行き止まりになり、合格の判定が不安定である（3.3、3.4、4章の G0、9章）**
- 3.3 は校正を「プロンプトを固定する前に」行うとする。G0 と G1 のプロンプトは G-boot でハッシュを固定し「以後は変更しない」。G0 の通過条件に「レビュアーの校正に合格」がある。不合格なら「そのプロンプトは使えない」が、変更の経路がない（4.1 の表にも入っていない）。G0 で計画は停止する。
- 欠陥5件で 3分の2 以上は、実質4件以上である。真の検出率が 80% のレビュアーの合格率は 74%、90% でも 92% である。G0 と G1 の4名がすべて合格する確率は、それぞれ 30%、71% である（再試行の規定がなく、2名のゲートで個別か和集合かも未定）。
- G2 以降の校正は P1 で行うと定めているが、P1 の時点には雛形、ログ、分析のコードが存在せず（P2 以降）、実行できるイメージもない。実行型のゲートの校正には偽の成果物一式が必要で、その作者（P1）は仮説を知っている。費用も 6章に計上されていない。

対応：校正の失敗時の経路（プロンプトの修正と再校正の上限）を bootstrap の段階で定める。合格の判定は件数を増やすか複数回で行う。後段の校正の時点を、実物の成果物ができる時点まで移す。

**N-7 2回目で見つけた差分外の `major` の行き先がなく、未解決の `major` に上限がない（3.2 の4と6）**
2回目の判定の項目は「全体の新しい `critical`」と「差分の中の新しい `major`」だけである。差分の外で実際の `major` を見つけた場合の出力先がなく、「2回目で残った `major`」に当たるかも読み取れない。1名のゲート（G2〜G7、G9、G10）では、1回目の1名が見落とせば最終報告にも残らない可能性がある。

また、`major` の定義は「妥当性…を実質的に損なう」であるのに、「修正できない `major` は未解決として同じ一覧に載せる」だけで進行する。13のゲートにわたる累積の上限がなく、後段のフェーズの作成者とレビュアーにも渡されない。たとえば G3 の未解決の `major`（仕様の偏り）を持ったまま 2,400 USD の本実験まで進み、その影響を判断するのは最終の人間である。3回目を行わないのは要件どおりだが、その場合に必要な歯止めが欠けている。

対応：差分外の `major` を「記録のみ」として出力できるようにし、最終報告に載せる。未解決の `major` の一覧を後段のレビュアーに渡す。G8 の前に、累積した未解決の `major` の結論への影響を判定する項目を置く。

**N-8 棄却率 30% の規則は、指摘が少ないゲートで誤検出を1件も棄却できない（3.2 の3）**
`critical` と `major` が1〜3件のゲートでは、1件の棄却で 33% 以上となり、不合格になる（棄却が許されるのは4件以上の場合のみ）。良質な成果物ほど指摘が少ないので、誤った指摘が1件あると、作成者は誤りを「修正」するか、ゲートを不合格にするかの選択になる。「不合格」の後の手順も定義がない（3.2 の分岐にない。7章の「上限内で通過しない」に当たるのかも不明）。分母が1回目だけか累積かも不明である。

失敗シナリオ：G3 で `major` 2件のうち1件が誤りで、裁定者も棄却を認める。それでも 50% でゲートは不合格になり、実験が止まる。

対応：件数の下限を設ける（例：棄却3件以上かつ 30% 超）。不合格は停止ではなく、棄却の裁定の再確認に回す。

### 予算と統計

**N-9 配分が固定で、計画自身の想定の範囲で停止する（6章、7章。M-23 の `not_fixed`）**
「パイロット、調整、試走」の 600 USD の計算：P5 は 160c（縮小で 96c）、P7 の試走は 144c（3課題 × 4条件 × 3回 × 4段階、縮小の手順なし）である。

| c（USD） | 10回 + 試走 | 6回 + 試走 | 6回 + 調整後の再実施 + 試走 |
|---|---|---|---|
| 1.5 | 456 | 360 | 504 |
| 2.0 | 608 | 480 | **672** |
| 2.5 | 760 | 600 | **840** |
| 3.0 | 912 | **720** | **1,008** |
| 4.0 | **1,216** | **960** | **1,344** |

6章の c の想定は 0.5〜4 USD である。c > 2.5 では調整なしでも、c > 1.8 程度で調整が1回あれば、この区分を超える。7章により停止する。c = 3 でも本実験の配分は n = 12.5 を賄えるので、配分の余りを動かさないことが原因で止まる。

同じ問題が他にもある。

- 「作成とレビュー」の 600 USD には積算がない。P3 と P7 の 20 セッション（要件と参照実装）、13 ゲートの 17 組で各2回のレビュー、修正、裁定、校正を合わせると 150 セッション前後になり、1回のレビューの費用は解答者の c より大きくなり得る。超過の手順がなく、2,400 USD が残っていても 7章で停止する。G4 の 16 セッションの区分も不明である。
- n の式は配分の全額を使うが、インフラの再実行（最大 10%）の余裕がない。n を上限に取ると本実験の途中で配分を超え、事前登録どおりに完了できない。

対応：区分間の移動の規則を事前に定める（本実験の配分から差し引き、P8 の検出力で判定する）。P5 の実測で全区分を再積算する。n には再実行分の余裕を含める。

**N-10 検出力の判定の入力が一意でなく、4課題では判定の結果が仮定で決まる（4.2 の2、P8、6章）**
6章は検出力の値で3つに分岐するが、次が未定である。

- 検定がどれか（H1 の TOST、H2、H3 のどれが「主要な検定」か。4.2 の6は `ts` 対 `js` と言うだけである）。
- 課題間の分散を「仮定の範囲」で扱うと、検出力は範囲になる。範囲のどの値で分岐するかが書かれていない。
- 自由度の扱い。4課題で課題×条件を含めるなら、実効の自由度は3程度である。

試算（`ts` 対 `js` の課題ごとの差の t 検定、自由度3。n = 25、試行の SD 0.20、真の差 10 ポイント、課題×条件の SD を τ とする）：

| τ | 差の検定（両側 5%） | 同等性（TOST、真の差0） |
|---|---|---|
| 0 | 66% | 71% |
| 0.05 | 45% | 42% |
| 0.10 | 24% | 13% |
| 0.15 | 15% | 4% |

τ が 0 に近くても 80% に届かないので、「確認的な研究」の分岐はこの試算の条件では起こらない。τ = 0.05 以上なら「実施しない」となる（片側検定なら τ = 0 で 84%、τ = 0.05 で 64%、τ = 0.10 で 39% であり、検定の向きの選択でも分岐が変わる）。この表は簡略化した試算で、検定は Holm 補正の前の値である。作成者が大きな自由度の Wald 検定で計算すると、検出力は高く出るが、第1種の過誤が増える。この選択で実施の可否が決まってしまうのに、G8 の観点に「最小の関心効果と検出力の明記」しかない。

また、4.2 の2の代替手順「課題クラスターのブートストラップ」は、4課題では異なる再標本が 35 通りしかなく、信頼区間の被覆を保証しない。課題単位の符号反転の検定なら組み合わせは 16 通りで、最小の p 値は両側 0.125 であり、5% に届かない。

対応：検定、τ の値（または値の決め方）、小標本の補正（Kenward-Roger など）を P1 で固定し、シミュレーションで第1種の過誤を確認してから分岐する。4課題の場合は、結論の範囲を「この課題群」に限定し、課題の一般化を確認的に主張しないことを事前に決めるのがよい。課題数を増やす案と費用も P8 で比較する。

**N-11 P7 の難易度の判定は信頼できず、やり直しに上限がない（P7、4.3、4.1）**
P7 は課題ごとに各条件3回（プールして12回）で、「各段階の全合格率が 10〜90%」を判定する。12試行では 2〜10 件でないと基準を外れる。真の全合格率が 15% または 85% でも 44%、20% でも 28% の確率で、基準を外れると判定される（4段階あるので、課題全体ではさらに高い）。一方、作り直しと「事前に用意した予備」は 4.1 の変更要求の回数に数えるのか不明で、上限がなく、予備の作成の工程と費用はどのフェーズにもない。1回の作り直しで試走は 48 セッション増える。N-9 の区分をさらに圧迫する。さらに、課題を基準の内側になるまで引き直すと、難易度で選択したことになる。

非公開テストは境界値と異常系が多いので（CONCEPT 6.3）、v4 の全合格率が全条件で 10% 未満になることもあり得る。その場合は基準の設計自体が合わない。P6 の時点で 40 試行で確認できるが、そのときの手順は変更要求（上限3回）を消費する。

対応：P7 の判定は全合格率の点推定ではなく、合格割合の範囲にするか、外れた場合の扱いに区間を使う。予備の工程と作り直しの回数の上限を定める。4.3 を P1 で確定する際に、シミュレーションで誤判定率を確認する。

### ログの逐次記録（5.5）

**N-12 ターンごとのコードの取得は、解答者に影響しない方法が確認されておらず、影響の検査もない（5.5 の「コードの変遷」と「解答者の環境に影響させない」、G4）**
5.5 は、API 要求の区切りごとに、ビルド成果物を除いた `/work` をホスト側から取得するとする。このマシンで使える手段を確かめると、どれにも問題がある。

| 手段 | 問題（実測） |
|---|---|
| `lxc file pull -r` | 除外のオプションがない（`--help`）。`target/` や `node_modules/` も転送するか、ホスト側で一覧を辿って個別に取得することになる。転送量と時間が条件で大きく変わる |
| `lxc exec` で `tar` などを実行 | 解答者のコンテナ内でプロセスが動く。`ps` で見え、2GiB の cgroup のメモリを消費し、条件で異なる OOM の要因になる。解答者に監視の存在を示唆する |
| ストレージプールのパスを直接読む | `/var/snap/lxd/common/lxd/storage-pools` は root のみで読めない（`drwx--x--x root`、一覧は Permission denied）。`sudo` も使えない |
| `lxc snapshot` | 取得自体は軽い可能性があるが、中身を読むにはコピーやエクスポートが要る。除外もできない |

失敗シナリオ：取得が要求を止める同期型なら、ターンごとの待ち時間が木の大きさに比例し、`rust` と `ts` だけ実時間が増える。H3 は時間も対象であり（CONCEPT 2）、5.1 の「参考扱い」の注記は他の負荷についてのものなので、この条件差には当たらない。非同期型なら、次のツール実行と重なって不整合な状態を保存し、「任意のターンのコードを復元できる」が成り立たない。`lxc exec` の場合は、解答者のビルドと同じ cgroup で動き、モデル側の結果と分類される OOM に影響し得る。

「取得方法は全条件で同じ」は手順の同一性であり、影響の同一性を保証しない。G4 の追加項目は復元の可否だけを確かめ、影響を確かめない。

対応：P0 で手段を決め、G4 に条件別の計測を加える（1ターンあたりの追加時間とメモリ、解答者の環境から観察できるもの、取得と次のツール実行の重なり）。取得時間を実時間の指標から差し引く。影響が基準を超える場合の代替（例：段階の終了時と `make test` の前後のみ。プロキシで検出できないなら、ツール結果の区切りのみ）を事前に決める。

**N-13 ログの仕組みの検証が P4 で初めて行われ、それより前のセッションの記録が保証されない（5.5、3.5、4章の G0 と G4）**
5.5 の対象は「全セッション」で、再実行できない作成者とレビュアーのセッションを含む。しかし、

- 検証の項目は G4 の行にだけ追加され、G0 の試験に入っていない。P1〜P3 の全セッションと G0〜G3 のレビューは、ハッシュの連鎖、`fsync`、コードの取得が未検証のロガーで記録される。欠陥が G4 で見つかっても、そのログは取り戻せない。
- 表の「P4 実行系」は「ログ保存」を成果物としており、P0 の成果物の一覧（`orchestrate.py`、`proxy/`、`containers/`）には記録の担当がない。P1 からのログを誰が作るかが読み取れない。
- 3.5 は `review.sh` を「新しいコンテナの作成、成果物のコピー、固定プロンプトでの実行だけ」とする。G-boot と G0 のセッションのログを `review.sh` が残す規定がない。3.3 の実行の照合はログのツール呼び出しの ID を必要とするので、G0 では照合の土台もない。

対応：共通のセッション起動とログの層を P0 の成果物とし、G0 の試験に強制停止と復元を加える。`review.sh` にも生ログの追記とハッシュの記録を含め、G-boot の対象にする。P4 は解答者に固有の部分だけを担当する。

## 4. Minor

- **m-1 ターンの定義（5.1）**：`/v1/messages` の要求数には、CLI の再試行とサブエージェントの要求が入る。API の一時的な障害がターンを消費する。また、プロキシが上限で止めると CLI は異常終了し、5.4 の「CLI 本体の異常終了」（インフラ）と「ターン上限」（モデル側）のどちらにも読める。G4 で基準を明確にする際に扱うこと。ターンの値も未定である。
- **m-2 費用上限の循環（5.1）**：上限は「パイロットの 99 パーセンタイルの3倍以上」だが、パイロット自体にも上限が必要である。初回の値の決め方がない。160 セッションからの 99 パーセンタイルはほぼ最大値である。
- **m-3 残高の確認（2.3）**：`start.py` は「残高」を少額で確認するとするが、通常の API キーで残高を読む手段は確認できない（Admin API は通常のキーを拒否する。`claude-api` の資料による）。少額の実行で分かるのは、残高が尽きていないことだけである。実行中に残高やワークスペースの上限に達した場合の応答の分類も 5.4 にない。
- **m-4 プロキシの代替の不足（5.2、5.1、5.5、7章）**：プロキシが使えない場合の切り替え先は鍵の配置だけを述べている。ターン上限（5.1）、モデルの検出（7章）、パスの制限（5.2）、API の記録とコード取得の区切り（5.5）もプロキシに依存するので、代替手段が必要である。ただし CLI は `ANTHROPIC_BASE_URL` を使えるはずで、発生の可能性は低い。P0 で確認される。
- **m-5 プロキシの検査の範囲（5.2）**：パスとモデル ID だけでは、`/v1/messages` の本文で指定するサーバー側のツール（`web_search`、`web_fetch`、`code_execution`、`mcp_servers`）を止められない。解答者が Bash からプロキシに直接要求すれば、Web の検索や Python の実行が使える。本文の `tools` と `mcp_servers` も許可制にし、G0 の試験に加えること。
- **m-6 プロキシへの到達範囲（5.2、G0）**：ホストのソケットを `ton` のブリッジの IP で開くと、他のブリッジの `workshop` のコンテナからも経路上は到達できる可能性がある。ダミーの鍵を照合しないと、実鍵で課金される。逆に、`ton` のコンテナからホストの他のサービスへの到達も G0 の試験の一覧にない（実測ではホストの 8000、5173 番は 127.0.0.1 のみで、DNS は `workshopbr0` の IP で待ち受けている）。
- **m-7 権限モードが未定義（3.1、5.1）**：第2版の共通フラグに `-p` と権限モードがない。`--no-session-persistence` は `--print` でのみ動く（実測）。権限モードは統制変数であり、root での実行の可否とあわせて P0 で固定すること。
- **m-8 確定したイメージの再試験（P0、P2、G2、G4、4.1）**：G0 の分離の試験は P0 の時点のイメージで行うが、解答者のイメージは P2 で作る。G2 と G4 と 4.1 の再通過に、カナリアと残留の試験がない。確定のイメージで再実行すること。
- **m-9 要求メモの作者（P3、P7）**：P3 の「中立な要求メモ」は CONCEPT 6.2 から作れるが、P7 の3課題のメモの作者がどのフェーズにもない。仮説を知る P1 が書けば、G7 の「作者に仮説を渡していない」を満たしたまま、段階の設計に偏りが入る。
- **m-10 パイロットのデータの扱い（P8）**：P8 の作成者が条件別のパイロットの結果を見られるかが定められていない（P6 にはプールのみの制限がある）。パイロットのデータを本実験の検定に使わないとする規定も第2版から消えている。G8 で確認できるが、明記すべきである。
- **m-11 無人の再開と待機（2.1、5.4、7章）**：5.4 の「再起動後に再開」には起動の主体がない。実測で `Linger=no` であり、利用者のサービスはログインがなければ動かない。`sudo` はパスワードが必要である。また「空き 5GiB 未満なら始めない」の待機に上限がなく、7章にも停止の条件がない。実測の available は 6GiB で、余裕は 1GiB しかない。他の用途の負荷が続くと、報告なしで止まったままになる。
- **m-12 レビュアーに渡す基準（3.1、2.2、3.3）**：3.1 はレビュアーに「原本の `CONCEPT.md` と `PLAN.md`」を渡すとする。P1 より後のゲートでは、原本は Docker や5種類の課題を述べており、誤った指摘を生む（N-8 に影響する）。原本と更新後の両方を渡すべきである。
- **m-13 冒頭の優先規則（1行目、2.2、6章）**：「2.2 の変更点に限り本計画を優先」とあるが、パイロットの 10回→6回は 2.2 になく、CONCEPT 7.2 と 9章の「10回」と矛盾する。CONCEPT 5 のトークン上限（第2版は費用上限）も同様である。2.2 に加えること。なお 2.1 の「ターン上限はプロキシで実施する（3.5 と 5.1）」の 3.5 は参照先が誤りである（3.5 にターン上限の記述はない）。
- **m-14 5.4 の分類の境界（5.1、5.4）**：2GiB の制限で cgroup の OOM が CLI 本体を止めた場合、原因がビルドなら「OOM」（モデル側）だが、現象は「CLI の異常終了」（インフラ）である。Rust と TS の負荷で条件差が出る箇所である。無出力 15 分と費用上限の発動も、どちらの分類かが書かれていない。
- **m-15 拒否の扱いとモデルの未定義（2.2、3.3、3.2、5.4）**：`stop_reason: refusal`（Opus 5.5 は `cyber` など、Sonnet 5.5 は5分類）の扱いがない。分離の攻撃を試みる G0 のレビュアーで起きやすく、`--fallback-model` も使わないので、3.2 の「異常終了」として2回の再実行の後にインフラ障害で停止する。また、1名のゲートのレビュアーと作成者のモデルと effort が定められていない（2.2 は解答者のみ、3.3 は2名のゲートのみ）。

**5.5 の追加に関するもの**

- **m-16 「改ざんを検出する」の範囲（5.5、3.5）**：`sudo` がないので、追記専用を OS で強制できない（`chattr +a` は root が必要）。ハッシュの連鎖は、同じ UID で書ける者なら全体を計算し直せる。コンテナ内のセッションには有効だが、P0 のホストセッションには効かない。3.5 は P0 の改ざんを人間が確かめる手順に「P0 セッションの全ログ」を挙げるが、そのログも P0 が書き換えられる（5.5 は「取得できる範囲で」とも緩めている）。開示の記述を実態に合わせるか、外部に置く基点（人間が開始時に控える値など）を定めること。
- **m-17 記録の失敗の扱い（7章、5.4）**：7章は「新しい試行とセッションの開始」を止めるだけなので、書き込みが失敗しても実行中のセッションは記録なしで続く。また、1回の書き込みの失敗で実験全体が止まるのか、一時的な失敗を再試行するのかの区別がない。ログが欠損した試行が 5.4 のインフラ失敗か、分析に含めるのかも定められていない。H3 の指標はログから作るので、これは欠損の扱いの問題である。
- **m-18 正規化イベントの妥当性と固定（5.5、4.2 の8、5.3、4.1）**：修正ループと型検査の回数は生ログの解釈で決まる。エージェントが `make check` でなく `tsc` や `cargo check` を直接実行した場合の数え方で、条件差が生じ得る。G4 には条件別の正解との照合がない。また、「再生成できる」ので結果を見た後に規則を変更できる。使う規則のバージョンを事前登録に固定し、変更を 4.1 の「判定に影響する」として扱うことを明記すること。
- **m-19 生ログの範囲（5.5）**：表は「全メッセージ」としているが、`--help` によると、サブエージェントの本文と思考を `stream-json` に流すには `--forward-subagent-text` が要る。共通フラグ（3.1）に入っていない。API の記録で補えるが、形式が分かれる。思考の本文については、表示の設定を変えて取得を増やす場合は統制変数なので、全条件で固定すること。
- **m-20 ログの量の見積もり（5.5、7章、G8）**：API の要求は毎回全履歴を含むので、量はターン数の2乗で増える。2,000 セッションの試算で、30 ターン・平均 200KB で 11GB、100 ターン・平均 400KB で 76GB、200 ターン・平均 800KB で 305GB である（これに圧縮コピーとコードの変遷が加わる）。実測の空きは 289GB で、他の用途でも使われる。ターン上限も未定なので、20GB の停止が本実験の終盤に発動し得る。P5 の実測から本実験の必要量を見積もり、G8 の条件に加えること。原本の圧縮の方針も必要である。
- **m-21 `runs/` と Git、渡す範囲の定義（5.5、3.1、4章）**：`runs/pilot/` は P5 の成果物でゲートの対象だが、5.5 によりコピーは Git に入らずマニフェストだけをコミットする。3.1 の「成果物全体の SHA-256」をどちらに適用するかを定めること。また「担当に必要な範囲だけを渡す」の範囲が未定で、3.1 の「作成者の会話、思考を渡さない」との境界（たとえば G5 に渡すログ、P6 と P8 に渡さない条件別のログ）をフェーズごとの一覧に明記すること。
- **m-22 G4 の試験の範囲（4章の G4、5.5）**：G4 の項目はセッションの強制停止だけである。規則が挙げるホストの再起動と、唯一の書き手である管理プログラムやプロキシ自身の異常終了を試験しない。ホストの再起動は他の用途に影響するので実施できないが、プロセスの強制終了は試験できる。「一定間隔で `fsync`」の場合、電源断では最後の間隔分が失われるので、「その時点までのログ」という記述は厳密には成り立たない。許容する損失の範囲を書くこと。

- プロキシで実鍵を付与し、コンテナにダミーの鍵を置く方式（CLI 側の前提は P0 で確認する）。ログイン認証をコンテナに入れないこと。
- 3.6 の実行型ゲートの制限、5.2 の監査の2層化、4.2 の失敗の持ち越しの方針、8章の開示の項目。
- 5.5 のうち次の点：ログをコンテナの外だけに置き解答者に伝えないこと、破棄した試行のログも消さず再実行を元の試行と結びつけること、実鍵を記録しないこと、思考の本文が取得できない可能性（Opus 5.5 の既定は本文なし）を開示し P0 で確認すること、未登録のログ分析を探索的として扱うこと。ログは 3.1 の制御領域と整合し、7章の停止条件と 8章の7にも反映されている。
