## 3. Major（記録のみ）

### R3-1 P0 の作成者の環境を P0 が作ると読め、適用の順序が循環する

**該当**：1章、3.1（作成者はコンテナで動く）、3.6（実鍵は `ton-proxy` だけ）、4章の PB と P0 の行、G-boot

**主張**：P0 の行は「`containers/` の定義を作り、ランナーが `ton` のプロジェクト、プール、ブリッジ、基本イメージ、プロキシを適用する」とする。しかし定義を書く P0 の作成者は、`ton` のコンテナ、イメージ、ブリッジ、API のプロキシがないと起動できない。一方で G-boot は P0 より前に「`ton` での模擬の実走」を要求する。PB の成果物には、この最小の環境が明記されていない。

さらに、イメージに入れる Claude Code の入手元が定まっていない。プロキシの許可先（3.2）は apt、npm、crates.io、PyPI、Rust と Node の公式配布先だけである。ネイティブ版はホストの `~/.local/share/claude/versions/2.1.316` にあるが、定義からホストのファイルを取り込む手段は規定がない。

**失敗シナリオ**

1. `bootstrap/` が最小の環境を作り、P0 の定義が同じブリッジとプロキシを適用し直す。実行中の P0 の作成者自身の通信が切れ、インフラ障害として扱われる。
2. 2つの構成が並存し、G0 の試験がどちらを対象にするかが実装の都合で決まる。試験に通った構成と本実験の構成が異なる。

**対応案**：プロジェクト、プール、ブリッジ、ACL、`ton-proxy`、作成者とレビュアーのイメージは `bootstrap/` の担当として PB の成果物に明記する。P0 の定義は解答者のベースイメージなどの追加に限る。Claude Code の取り込みは、ランナーの固定の手順にする。

### R3-2 G-boot の試験を誰が実行するかが定まっていない

**該当**：3.6、4章の PB の行、3.4（実行の照合）

**主張**：G-boot は「単体試験と、`ton` での模擬の実走が通る」を条件とするが、実行主体が書かれていない。この時点で窓口はなく、固定のランナーは検証の対象そのものである。N-1 の表に G-boot はなかったが、同じ種類の欠落である。

**失敗シナリオ**：開始前のセッションが試験を実行し、ログをレビュアーに渡す。レビュアーはそれを読むだけで通過させる。ランナーと分離試験の欠陥は、G0 の実行者自身の欠陥なので、G0 でも見つからない可能性がある。

**`critical` にしない理由**：開始前のセッションとレビュアーはどちらもホストで動くので、レビュアー自身が再実行できる。つまり仕組みは成立し、書かれていないだけである。

**対応案**：G-boot のレビュアーが、試験と模擬の実走を自分で実行することを必須にし、そのツール呼び出しを照合の対象とする。

### R3-3 定義の検査が「`ton` かどうか」だけで、`ton` の中からホストに届く

**該当**：3.1（ランナーができないこと）、3.2（「適用先は `ton` だけで、それ以外を指す定義は拒否する」）、1章（「LXD、制御領域、公開の手段に触れられない」）

**主張**：3.2 の検査の基準は適用先だけである。LXD の制限のないプロジェクトでは、次の定義は `ton` の中で有効である。

- `disk` デバイスで `source=/home/coxless/.local/share/typed-or-not/control` や `~/.config/typed-or-not/api_key`、`~/.claude/.credentials.json` をマウントする
- `disk` デバイスや `proxy` デバイスで LXD のソケットを渡す
- `security.privileged=true`、`raw.lxc`、`raw.idmap` を設定する
- 適用先が `ton` なので `ton-proxy` の定義も変更できる

既存の `workshop.coxless` には `restricted` の設定がない（`lxc project show`）。`ton` の設定について第3版に規定がなく、G0 の「作成者役のゲート迂回」の範囲にも明記がない。サーバーは `projects_restrictions` に対応している。

**失敗シナリオ**：P2 の作成者が、定義に制御領域のマウントを含めてランナーに適用させ、窓口のコンテナから条件名の対応表や実鍵を読む。適用先は `ton` なので検査を通る。

**対応案**：`ton` を `restricted=true` とし、`restricted.containers.privilege=unprivileged`、`restricted.devices.disk`、`restricted.devices.proxy` などを固定する。定義は宣言形式とし、キーの許可一覧で検査する（定義をホストのスクリプトとして実行しない）。`ton-proxy` の定義は窓口の対象から外す。G0 に、これらの定義が拒否されることの試験を加える。

### R3-4 P0 のコード取得の測定に、実行主体がない

**該当**：4章の P0 の行、5.5（「P0 で測定して決める」）

**主張**：第1候補はホスト側のバインドマウントとコピーで、測定には API 要求の区切りで動くホスト側の処理が要る。窓口は「新しい `ton` コンテナでコマンドを実行する」だけで、作成者もレビュアーもホスト側の処理を動かせない。PB の成果物にも測定の手順はない。これは N-1 と同じ種類の欠落だが、対象が N-1 の表の外にある。

**失敗シナリオ**：`bootstrap/` に測定の機能がなく、P0 の作成者が測定できない。作成者は代替を選ぶか、`bootstrap/` の変更要求を出すことになる。前者ではコマンドによる変更を再構成できなくなり、解消できるはずの制約を報告書に載せることになる。後者では G-boot と G0 の再通過が要る（4.1）。

**`critical` にしない理由**：代替が定められていて、G4 で影響を測定する。

**対応案**：両方の取得方法と測定の手順を `bootstrap/` に入れ、測定をランナーの固定の試験にする。選択の基準（ターンあたり 1 秒、観察可能性）は機械的に判定する。

### R3-5 P4 の作成者がゲートの前に実走で確かめる経路が不明確

**該当**：3.2（「解答者の試行」）、4章の P4 の行、3.3 の8

**主張**：3.2 の窓口は要求されたコマンドを新しいコンテナで実行するが、試行の実行は試行実行部の担当である。P4 の作成者が試行の実行を要求できるか、G4 の完走を誰がいつ起動するかが書かれていない。

**失敗シナリオ**：作成者が書いた設定の誤りが、G4 の実走で初めて現れる。監査と正規化のスクリプトは、実 API の `stream-json` を P0 の少量のサンプルでしか試していない。通常の不具合が G4 の指摘になり、回数の上限（4回）と全段階の API 費用を消費する。

**`critical` にしない理由**：G4 は修正が許されるゲートで、実行部自体は模擬の実走を通っている。4回で止まれば報告して停止するので、無効な結果にはならない。

**対応案**：P4 の作成者に、費用の上限つきで「1条件1段階」の試行を要求できる窓口を与える。G4 の完走は管理プログラムがレビューの前に起動し、その生ログをレビュアーに渡す。

## 4. Minor（記録のみ）

- **m-1 窓口の返却の手順がない（3.2）**：要求の受け取りと、結果をコンテナに返す方法、セッションの待ち方が未定である。`lxc file pull` と `lxc file push` によるポーリングで実現できるが、`-p` のセッションで Bash ツールの時間制限より長いビルドを待つ方法、ランナー側の時間制限、タイムアウトの分類を決める必要がある。
- **m-2 「コマンドの許可一覧」の対象が曖昧（3.1、3.2）**：コンテナ内のコマンドの一覧と読むと、一覧は G-boot で固定されるのに、`make` の中身や分析のスクリプトは P2 と P4 で決まる。不足のたびに `bootstrap/` の変更要求が必要になり、回数の上限を消費する。許可一覧はホスト側の `lxc` の操作に対するものとし、使い捨てコンテナの中のコマンドは制限しないと明記すること。
- **m-3 「`ton` 以外の操作」の範囲が LXD の構造と合わない（3.1、3.2、P0）**：ストレージプールはサーバー全体の資源である。実測では `workshop.coxless` にネットワークの機能がなく（`NETWORKS: NO`）、`workshopbr0` は `default` に属する。LXD のブリッジはプロジェクトごとに持てないはずで（コンテナを作らずに確かめられないので、未検証の主張とする）、`ton` のブリッジと ACL も `default` の名前空間に置くことになる。検査をプロジェクト名だけで行うと適用が拒否される。逆に `default` を丸ごと許せば `workshopbr0` も変更できる。`ton` の接頭辞を持つ名前に限る、などの規則を定めること。
- **m-4 窓口の資源の制限が要求の形式にない（3.2、G3、5.1）**：G3 は 2GiB を要求するが、3.2 に窓口のコンテナの制限の記述がない。解答者と同じ制限を固定で適用すること。窓口のコンテナと同時実行の上限や空きメモリの条件（2.1）との関係も未定である。実測の available は 6.1GiB、スワップの使用は 2GiB で、余裕は小さい。
- **m-5 窓口の実行が成果物のどの版かに結びつかない（3.2、3.4）**：作成者が古い版で実行したログを、照合に使える余地がある。ランナーのログに対象のファイルのハッシュを記録し、照合では最新の成果物と一致するものだけを有効とすること。
- **m-6 管理プログラムの強制終了の試験（G0、5.5）**：ランナーは管理プログラムの一部なので、自分自身を止める試験はそのまま実行できない。試験用の別インスタンスを起動する方式を PB で定めること。同様に、本物の `ton-proxy` を止める試験は、実行中のセッションがないときに行う必要がある。
- **m-7 分離試験の陰性対照がない（3.2、G0、5.2）**：イメージを最小にすると、`curl` などがないために「通信できない」となり、試験が見かけ上合格する。遮断を外した対照のコンテナで試験が失敗することを、G-boot で確かめること。
- **m-8 ランナーの再開（2.3、3.1）**：`crontab` の環境の `PATH` に `/snap/bin` は通常含まれないので、`lxc` は絶対パスで呼ぶ必要がある。起動直後は snap の LXD が準備中の場合があり、再試行が要る。`disposition.md` は `@reboot` の動作を G-boot で確認するとしているが、他の用途のコンテナが動くマシンを再起動して試験できるかは決まっていない。端末の終了で `start.py` が止まらないように切り離す処理も必要である。
